# Prototype: Real Questions from `Brain_Anatomy_Sample.pptx`

Week 7 of 12. Scope: generate multiple-choice, short-answer and picture-based questions from a real four-slide lecture deck using Claude Sonnet, serve them from the existing Next.js app, and ship it through the Cloudflare tunnel already running on the lab VM.

> **Status (2026-09-12): this is the design, not what shipped.** The generation half — every
> Claude call, prompt, schema and cost figure in §3 — is **not built**. The prototype's 22
> questions were hand-authored from the deck and committed as JSON, then adversarially
> fact-checked, because the goal was a working demo rather than a working pipeline. Everything
> downstream of generation *is* built and verified: the data shape, blanking, grading, the
> study UI and the deployment. Read §3 as the specification for `web/lib/llm.ts`, which is the
> next step; read §2 and §4 onward as describing code that exists. The measured finding in §1 —
> that this deck is entirely Tier 2 — was confirmed and drove the hand-authoring decision.

> **Superseded in part (2026-10-26).** Two decisions here no longer hold; `CLAUDE.md` is current
> on both. (1) §1's decision to send the rendered slide to Sonnet with vision and have it return
> normalised boxes: Tier 2 boxes now come from Tesseract OCR (`ingest/app/ocr.py`), the model
> only picks labels and writes synonyms and confusables, and vision boxes are a fallback behind
> §3.7's validation. (2) The provider and models: calls go through OpenRouter's
> Anthropic-compatible endpoint (`baseURL: "https://openrouter.ai/api"`, `OPENROUTER_API_KEY`)
> on Sonnet 5.5 and Haiku 5.5, not `claude-sonnet-5` with `ANTHROPIC_API_KEY`.

## 1. Context

### What already exists and works

| Part | State |
|---|---|
| `ingest/app/detect.py` | Tier 1 labelled-diagram detection from PPTX XML (shapes, EMU → normalised boxes, group recursion) |
| `ingest/app/render.py` | LibreOffice → PDF → PyMuPDF page render; `snap_label_box` snaps XML boxes onto drawn text |
| `ingest/app/blank.py` | Pillow blanking with numbered discs |
| `ingest/app/cli.py` | `sample`, `inspect`, `blank` |
| `web/lib/grading.ts` | CLAUDE.md's rule order — normalise → exact → synonym → reject confusable → reject another blank's answer → Levenshtein ≥ 0.85. **13 passing Vitest cases** |
| `web/data/questions.json` + `web/public/questions/*.png` | Committed question artifacts from the synthetic `sample.pptx` |
| `web/app/questions/[id]/` | Renders the blanked image, grades in a Server Action, reveals the original |
| Deployment | Production container on a Windows lab VM inside WSL Ubuntu, `cloudflared` quick tunnel (`--protocol http2`), `scripts/launch.py` / `shutdown.py` print the URL and a QR code |

No auth, no database, no upload flow, no queue. Questions are produced offline and committed as files. **That property is kept for this milestone, deliberately — see §6.**

### What this milestone adds

Real questions from a real deck, of three shapes — multiple choice, short answer, and picture-based — generated by `claude-sonnet-5`, plus the data, grading and UI to run them as one mixed quiz on a phone.

### The measured finding that drives the design

Running the existing Tier 1 path over `Brain_Anatomy_Sample.pptx` (4 slides, 960×540 pt) produces **an empty `questions.json`**. Zero labelled diagrams across all four slides. Two independent causes:

1. **Every slide reports `slide.shapes.title → None`.** The titles are ordinary `TEXT_BOX` shapes, not title placeholders. `detect.py:279-281` reads `shapes.title` and gets nothing on a deck built the way real decks are built.
2. **Slide 3 misses detection by exactly one label**, and the one label it found is the title:

| Check | Slide 3 value | Threshold | Result |
|---|---|---|---|
| "Lobes of the Brain" word count | 4 | `max_label_words = 5` | counts as a **label** |
| Gap, title box → picture | 22.9 pt | `0.06 × 960 = 57.6 pt` | attaches to the picture |
| Caption "Each hemisphere…" | 10 words | 5 | excluded |
| Labels attached | **1** | `min_labels_per_diagram = 2` | not a diagram |
| Picture area fraction | 0.305 | `min_ocr_picture_area_frac = 0.05` | → **Tier 2 OCR candidate** |

Because there is no placeholder, `FURNITURE_PLACEHOLDERS` (`detect.py:22`) cannot filter the title out. That is not only a miss: on another deck, a heading plus a caption near a picture would produce a **false** `labeled_diagram` whose "labels" are furniture. Fixing the title lookup (§4.6) is a correctness fix, not cosmetics.

**Slide inventory, measured:**

| Slide | Content | Slide text |
|---|---|---|
| 1 | Title, subtitle, Johns Hopkins Medicine attribution | — |
| 2 | "What Is the Brain?" — 6 bullets | ~516 chars |
| 3 | "Lobes of the Brain" — one large picture, **labels baked into pixels** | 78 chars |
| 4 | "Lobe Functions" — 3×5 table (header + 4 rows) | table |

Picture box on slide 3, normalised to the slide: `x 0.2485, y 0.2024, w 0.4782, h 0.6376`. Used as a validation rail in §3.7.

### Consequence

The XML route reaches nothing on slide 3. The hero feature must come from a different source. **Decision: send the rendered slide image to `claude-sonnet-5` with vision and have it read the baked-in labels, choose what to blank, and return normalised boxes.**

Honest tradeoff against Tier 2 OCR:

- **For vision:** Tesseract is not in the `ingest` image (only LibreOffice is), so Tier 2 is net-new container work. OCR returns words with boxes but no judgement — you still need a Claude call to pick testable labels and write synonyms and confusables. OCR therefore does not remove an API call; it adds a dependency.
- **Against vision:** OCR's boxes are pixel-accurate and **Claude's are not**. Reading is strong; precise coordinates are the weakest part of this design. A box off by 5% of image width covers the diagram instead of the word — a visibly broken question that fails silently.

Three mitigations, all taken: ship coordinate-free picture questions first (§2), validate every box in code and drop failures (§3.7), and keep generation offline so a human sees the blanked PNG before a student does (§6). If box quality proves bad, the contingency is Tier 2 OCR for boxes with Claude still choosing labels — every prompt and schema below stays unchanged. Do not build it yet.

## 2. Question types, mapped to the four real slides

| Slide | Generate | Route | Why |
|---|---|---|---|
| 1 | **nothing** | — | Title + subtitle + credit has no assessable content. Skip slides whose only text is furniture. |
| 2 | 3 × `mcq`, 1 × `short_answer` | R1 `text` | Contrastive pairs (grey vs white matter, CNS composition) — the one genuine essay on this deck. |
| 3 | 1 × `diagram_blank` (2–4 blanks) + 2 × `mcq` **with image** | R3 `vision` | The hero. Nothing but vision or OCR reaches these labels. |
| 4 | 1 × `table_blank` (4 cells) + 1 × `mcq` | R2 `table` | Geometry is exact from XML — zero coordinate risk. **Ship this first.** |

**"Picture question" is a property, not a type.** `image` is an optional field on the question base. A picture MCQ shows the unmodified slide and needs no boxes, no blanking and no new grading code — so the deck yields image questions on day one even if the vision boxes turn out unusable.

**What slide 4 should yield** — one blank per row, varying the column, every answer ≤ 4 words:

| Row | Blanked cell | Answer | Clue left visible |
|---|---|---|---|
| 0 | Lobe | Frontal | Front of the head · Personality, decision-making, movement, speech |
| 1 | Location | Middle of the brain | Parietal · Object identification, spatial relationships, pain and touch |
| 2 | Lobe | Temporal | Sides of the brain · Short-term memory, speech, musical rhythm, smell |
| 3 | Location | Back of the brain | Occipital · Vision |

The `Main functions` cells are never blanked: long sentences make ungradeable blanks, and they are the clue that makes the row answerable.

## 3. Generation design

### 3.1 Routes

| Route | Slides | Model | `effort` | Image | Schema | Prompt file |
|---|---|---|---|---|---|---|
| R1 `text` | 2 | `claude-sonnet-5` | `medium` | no | `TextQuestionSet` | `web/lib/prompts/text-questions.ts` |
| R2 `table` | 4 | `claude-sonnet-5` | `low` | no | `TableQuestionSet` | `web/lib/prompts/table-questions.ts` |
| R3 `vision` | 3 | `claude-sonnet-5` | `high` | yes | `DiagramQuestionSet` | `web/lib/prompts/diagram-vision.ts` |

**Effort is set per route, never inherited** (CLAUDE.md). R2 is mechanical selection over five rows — `low`. R1 is extraction plus distractor writing — `medium`. R3 must read small baked-in text, place coordinates and invent confusables, and confusable quality decides whether the grader works — `high`. Nothing here justifies `max`.

**All three routes run on Sonnet 5 this milestone**, despite CLAUDE.md routing simple text MCQs to Haiku 4.5. Reason: Haiku's minimum cacheable prefix is 4096 tokens (Sonnet's is 1024), so caching on the Haiku path would silently do nothing, and Haiku's thinking/effort configuration differs from Sonnet's — it is a different call shape, not a model-string swap. A full regeneration of this deck costs about five cents (§3.9), so the split buys a fraction of a cent for three code paths. Put the ids in one `ROUTES` constant with the reason in a comment so week 8 flips them in one line.

### 3.2 Dependencies

```bash
npm --prefix web i @anthropic-ai/sdk zod server-only
npm --prefix web i -D tsx          # fallback only; Node 26.7 on the Mac strips TS natively
```

`zod` is currently present in `web/node_modules` only as a transitive dependency and is **absent from `package.json`** — it disappears on a clean install. `server-only` is not installed at all (`client-only` is). Both must become explicit dependencies.

### 3.3 Call shape

```ts
// web/lib/llm/client.ts
import Anthropic from "@anthropic-ai/sdk";

// Reads ANTHROPIC_API_KEY from the environment. Never a literal key, never a
// Client Component, never NEXT_PUBLIC_*.
export const client = new Anthropic();
```

```ts
// web/lib/llm/call.ts  — one function, all three routes
import { z } from "zod";
import { client } from "./client";

export async function callRoute<T extends z.ZodTypeAny>(opts: {
  system: string;
  userContent: Anthropic.ContentBlockParam[];
  effort: "low" | "medium" | "high";
  schema: T;
  jsonSchema: Record<string, unknown>;
}): Promise<z.infer<T>> {
  const response = await client.messages.create({
    model: "claude-sonnet-5",
    max_tokens: 8000,
    system: [
      { type: "text", text: opts.system, cache_control: { type: "ephemeral" } },
    ],
    output_config: {
      effort: opts.effort,
      format: { type: "json_schema", schema: opts.jsonSchema },
    },
    messages: [{ role: "user", content: opts.userContent }],
  });

  const text = response.content.find((b) => b.type === "text");
  if (!text) throw new Error("no text block in response");
  return opts.schema.parse(JSON.parse(text.text));   // Zod is the gate, always
}
```

Vision route user content — **image block first, then text**, because the image is the subject:

```ts
const png = await fs.readFile(slidePngPath);
const userContent = [
  { type: "image", source: { type: "base64", media_type: "image/png",
                             data: png.toString("base64") } },
  { type: "text", text: slideContextBlock },
];
```

`data` is bare base64: no `data:` URI prefix, no newlines. `media_type` matches what `render_page` writes.

**Diagram blanks and image MCQs come back in one call.** The model sees the figure once and keeps its distractors consistent with the labels it chose to blank; it also halves the image cost.

**Hard API rules from CLAUDE.md, both enforced by the API:** no `temperature` / `top_p` / `top_k`, and no assistant-turn prefill — either returns 400 on Sonnet 5.

**SDK surface that needs confirming on the first call** — see §10. The code above deliberately uses `messages.create` plus a manual `JSON.parse` + Zod validate, which is the least-invented surface. Newer SDKs may expose `messages.parse()` and a `zodOutputFormat()` helper that remove the parse step; adopt them only after seeing them work.

### 3.4 Schemas

```ts
// web/lib/schemas/generation.ts
import { z } from "zod";

/** Normalised to the image sent in that request. Never pixels, never EMU. */
export const Box01 = z.object({
  x: z.number(), y: z.number(), w: z.number(), h: z.number(),
});

export const AnswerKeyFields = z.object({
  answer: z.string(),
  synonyms: z.array(z.string()),     // may be empty
  confusables: z.array(z.string()),  // may be empty — usually is
});

export const McqSchema = z.object({
  prompt: z.string(),
  options: z.array(z.string()).length(4),
  answer_index: z.number().int().min(0).max(3),
  explanation: z.string(),
  evidence: z.string(),              // verbatim quote from the slide
});

export const ShortAnswerSchema = z.object({
  prompt: z.string(),
  model_answer: z.string(),
  rubric: z.array(z.object({
    text: z.string(),
    weight: z.number().int().min(1).max(3),
    keywords: z.array(z.string()).min(1),
    confusables: z.array(z.string()),
  })).min(2).max(5),
  evidence: z.string(),
});

export const TextQuestionSet = z.object({
  slide_title: z.string().nullable(),
  mcqs: z.array(McqSchema).max(4),
  short_answers: z.array(ShortAnswerSchema).max(2),
});

export const DiagramLabel = AnswerKeyFields.extend({ box: Box01 });

export const DiagramQuestionSet = z.object({
  legible: z.boolean(),
  slide_title: z.string().nullable(),
  alt_text: z.string(),              // describes the BLANKED view — see §4.3
  labels: z.array(DiagramLabel).max(6),
  image_questions: z.array(McqSchema).max(3),
});

export const TableBlank = AnswerKeyFields.extend({
  row: z.number().int().min(0),      // 0 = first DATA row; header not addressable
  col: z.number().int().min(0),
});

export const TableQuestionSet = z.object({
  blanks: z.array(TableBlank).min(2).max(6),
});
```

Every field is required — no `.optional()` — because strict structured-output schemas want all properties required with `additionalProperties: false`. "Nothing to report" is an empty-but-present array.

**The constraint that matters is not expressible here.** `min`/`max` survive JSON Schema conversion; "this box lies inside the picture" does not. The schema is the *shape* gate; §3.7 is the *correctness* gate.

### 3.5 Prompts

One file per question type under `web/lib/prompts/`, exported as frozen constants. **Nothing interpolated** — no slide text, no ids, no dates — or the cached prefix changes on every request.

`web/lib/prompts/diagram-vision.ts`:

```
You turn a lecture slide into exam-style questions about its diagram.

You are given one rendered slide image and the text that the slide FILE contains
as separate text objects. Anything you can read in the image but that is absent
from that text list is printed inside the picture itself. Those are the labels
worth testing, because a text-only study tool cannot see them at all.

Return JSON matching the supplied schema. No prose outside it.

## Coordinates
Every box is normalised to the WHOLE IMAGE you were given: x and y are the
top-left corner, w and h the size, each between 0 and 1. x=0 is the left edge,
y=0 the top edge.

A box must tightly enclose that label's own text and nothing else — not the
structure it points to, not its leader line, not a neighbouring label.

If you are not confident of a label's position to within about 2% of the image
width, omit that label. A blank drawn in the wrong place is worse than one
question fewer.

## Choosing what to blank
Blank 3 to 6 labels naming parts a student is expected to recall. Skip:
- the slide title, headings, captions, and body text
- figure numbers, slide numbers, source credits, copyright lines
- axis units, scale bars, anything that is not the name of a part
Prefer a set learned together (all four lobes) over isolated incidental labels.

## Synonyms
For each answer, list the other forms a marker would accept: accepted
abbreviations, the expansion of an abbreviation, British/American spellings, and
the same structure's alternative name. Never list a DIFFERENT structure as a
synonym. Example: answer "Occipital lobe" -> synonyms ["occipital"].

## Confusables
List terms a student might plausibly write that look almost identical to the
answer but are WRONG — usually a domain opposite. The grader accepts a
Levenshtein ratio of 0.85 to forgive typos, which would otherwise let these
through: afferent/efferent (0.875), abduction/adduction (0.889),
hyperthyroidism/hypothyroidism (0.867).

Only list a confusable if it is a real term in this subject AND spelled close to
the answer. Most answers have none. Return an empty list rather than padding it —
a wrong confusable marks a correct student wrong.

## Image-grounded questions
Also write 2 to 3 multiple-choice questions answered by LOOKING at this image,
which cannot be answered from the slide's text alone. The student sees the
unmodified image, so these need no coordinates. Use them for spatial
relationships ("which lobe sits directly behind the frontal lobe?"), for reading
a value off the figure, or for identifying a region by its position. Do not write
a question whose answer already appears in the slide's text list.

## Alt text
Write "alt_text" describing the BLANKED view only — the figure and that some
labels are covered. Alt text is public. Never name a covered label in it.

## Legibility
Set "legible" to false if label text is too small or blurred to read with
confidence, and return no labels. Never guess at unreadable text: a wrong answer
key silently marks correct students wrong.
```

`web/lib/prompts/text-questions.ts`:

```
You write exam-realistic questions from one lecture slide's text.

Return JSON matching the supplied schema. No prose outside it.

Every question must be answerable from the slide text you are given and nothing
else. The student is revising this unit, not the whole subject: a question
needing outside knowledge is a wrong question here.

## Multiple choice
- Exactly 4 options, exactly one correct.
- Distractors must be plausible to someone who half-learned the slide: the other
  items from the same list, a near-miss number, a swapped pair of terms. Never a
  joke option, never one obviously absent from the slide.
- Never "all of the above" or "none of the above".
- Keep options a similar length. The longest option must not be the answer.
- One idea per question. If the slide supports two good questions, write two.

## Short answer
- The question must require 2 to 4 sentences, not a single word.
- Give a model answer and a rubric. Each rubric point has: the point in the
  marker's words, an integer weight, keywords (any one phrasing that counts as
  covering it), and confusables (near-miss phrasings that must NOT count).
- Prefer "explain the difference between X and Y" or "why does X matter" over
  "list the X", which is only recall.

## Grounding
For every question, put in "evidence" the exact sentence from the slide text it
came from, copied verbatim. If you cannot quote one, do not write the question.

## Title
Lecture slides often have no title placeholder, only a text box at the top. Set
"slide_title" to the heading if you can identify one, otherwise null. Do not
invent a title from the body text.
```

`web/lib/prompts/table-questions.ts`:

```
You turn a lecture slide's table into a fill-in-the-blank exercise.

Return JSON matching the supplied schema. No prose outside it.

The table arrives as a header row plus data rows. Row 0 is the FIRST DATA ROW —
the header is not addressable and must never be blanked. Columns are indexed
from 0, left to right.

- Blank at most one cell per row, and leave at least two cells in that row
  visible, so the row still poses an answerable question.
- A blanked cell's text must be at most 4 words. Long descriptive cells make
  ungradeable blanks — leave them visible; they are the clue.
- Vary which column you blank, so the exercise is not one column deleted.
- Never blank every row of a column, and never blank a whole row.
- Give synonyms and confusables per blanked cell under the same rules as diagram
  labels: only real terms, empty lists rather than padded ones.
```

### 3.6 Image sizing and one coordinate frame

**The image sent to Claude, the image served to the student, and the image Pillow blanks are all the same full rendered slide** at the existing `render_page(page, 2.0)` — 1920×1080. No cropping, no re-normalisation. One frame, so Claude's boxes are directly the boxes drawn and directly the boxes the browser sees. This is the single largest simplification in the design: it deletes the crop → re-normalise round trip in `cli.py:_fractions`.

| Render | Pixels | Visual tokens `ceil(w/28)×ceil(h/28)` | Input cost @ $2/MTok |
|---|---|---|---|
| zoom 1.0 | 960×540 | 35 × 20 = 700 | $0.0014 |
| zoom 1.5 | 1440×810 | 52 × 29 = 1508 | $0.0030 |
| **zoom 2.0 (default)** | **1920×1080** | **69 × 39 = 2691** | **$0.0054** |
| picture crop @ zoom 4.18 (legibility fallback) | 1919×1439 | 69 × 52 = 3588 | $0.0072 |

zoom 2.0 hits CLAUDE.md's 1920 long-edge cap exactly, and 2691 matches CLAUDE.md's own figure. Both rows are inside Sonnet 5's high-res tier (2576 px long edge, 4784 visual tokens).

**Legibility fallback needs no new code.** `zoom_for(crop, base_zoom, max_px)` already takes `base_zoom` (`render.py:86`). If R3 returns `legible: false`, re-render the picture region alone at `base_zoom=4.18` and retry once — recording that the coordinate frame for that retry is the crop, not the slide. If it returns `false` again, emit only the image MCQs and mark the diagram question `failed` with a user-legible reason: *"Couldn't read the labels printed inside the figure on slide 3."*

### 3.7 Box validation — the check that makes vision safe to ship

```ts
// web/lib/llm/validate-boxes.ts
const PICTURE = { x: 0.2485, y: 0.2024, w: 0.4782, h: 0.6376 }; // measured, slide 3
```

Reject a label — **drop it, never silently clamp** — when any of these hold:

- `x`, `y`, `w`, `h` outside `[0,1]`, or `x+w > 1`, or `y+h > 1`
- the box is not fully inside the picture box, with a 1% tolerance
- `w*h > 0.05` of the image — a label blank that large is a coordinate error, not a long label
- `w*h < 0.0002` — too small to have found real text
- IoU > 0.3 with another returned box — duplicated or merged labels
- `answer` appears verbatim in the slide's text-object list — the model re-read a text box instead of the picture

Fewer than 2 surviving labels → no `diagram_blank` for that slide. Keep the image MCQs, log why.

### 3.8 Prompt caching

Render order is `tools → system → messages`; there are no tools, so the breakpoint is `cache_control: {type: "ephemeral"}` on the single system text block, per route. Slide text and the image sit after it in `messages` because they change per slide — this is the shared-prefix / varying-suffix case where automatic top-level caching would be actively wrong. Default 5-minute TTL is right: a CLI run fires its calls seconds apart. **Pin `effort` per route** — changing it between requests invalidates the cache, another reason it belongs in `ROUTES`. Caches are per model, so a Sonnet/Haiku split forfeits reuse.

At ~3 calls per deck this saves well under a cent. Wire it because the code path is right for week 8 volume, not because it pays today.

### 3.9 Logging and cost

No database exists, so append one JSON line per call to `logs/llm-requests.jsonl` with the `llm_requests` columns from CLAUDE.md — `{id, route, model, slide_index, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, batch: false, cost_usd, created_at, source_ref}`. Moving to Postgres in week 8 is then a sink swap, not a schema change. `logs/` is **not** currently in `.gitignore` — add it; token counts are dev telemetry, not an artifact.

`batch` is `false` everywhere: everything generates synchronously this milestone.

```ts
// web/lib/llm/log.ts
const PRICES = {
  "claude-sonnet-5":  { in: 2.0, out: 10.0 },  // $ per MTok, per CLAUDE.md
  "claude-haiku-4-5": { in: 1.0, out:  5.0 },
} as const;

export function costUsd(model: keyof typeof PRICES, u: Anthropic.Usage): number {
  const p = PRICES[model];
  return (
    u.input_tokens * p.in +                            // uncached remainder only
    u.output_tokens * p.out +
    (u.cache_read_input_tokens ?? 0) * p.in * 0.1 +    // $0.20/MTok on Sonnet 5
    (u.cache_creation_input_tokens ?? 0) * p.in * 1.25 // 1.25x write premium — confirm, §10
  ) / 1_000_000;
}
```

**`input_tokens` is the uncached remainder, not the total prompt.** Total prompt = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`. Adding cache fields on top of a total you assumed was complete double-counts.

## 4. Data on disk, and grading

### 4.1 Split the files by trust boundary

The current single `questions.json` holds prompts and answers in one object. That survives one question type whose consumer is a server component, and stops surviving the moment MCQs exist: an MCQ's **options must reach the browser** while its key must not. One careless `<QuestionCard question={question} />` ships the answer.

```
web/data/questions.json     Question[]    — everything the browser may see   (committed)
web/data/answers.json       AnswerKey[]   — everything it may not            (committed, private repo)
web/public/questions/*.png                — blanked / picture renders, publicly served
web/data/reveals/*.png                    — un-blanked renders, NOT publicly served
```

Both JSON files stay plain committed files with no database, so `scripts/launch.py` keeps working and a fresh clone has everything it needs. Joined by `id`.

### 4.2 Public types — `web/lib/questions.ts` (rewritten)

```ts

export type OptionKey = "A" | "B" | "C" | "D";

/** width/height prevent layout shift on phones. */
export type ImageRef = {
  src: string;      // "brain-slide-03.png", served from /questions/
  width: number;
  height: number;
  alt: string;      // describes the BLANKED view — never names a covered label
};

type QuestionBase = {
  id: string;
  source_ref: string;            // "Brain_Anatomy_Sample.pptx, slide 3" — always populated
  title: string | null;
  image: ImageRef | null;
};

export type McqQuestion = QuestionBase & {
  type: "mcq";
  prompt: string;

};

export type ShortAnswerQuestion = QuestionBase & {
  type: "short_answer";
  prompt: string;
  guidance: string | null;       // "3-4 sentences" — instructions, not answers
  maxChars: number;              // hard cap, enforced server-side
  totalMarks: number;            // sum of rubric weights; safe to show
};

export type DiagramBlankQuestion = QuestionBase & {
  type: "diagram_blank";
  image: ImageRef;               // narrowed: never null
  prompt: string;

};

export type TableBlankQuestion = QuestionBase & {
```

Two deliberate subtractions from today's shape: `blanks[].answer` and `blanks[].box` both leave the public file. The boxes are not secret — the rectangles are visible in the PNG — but the browser has no use for them, since Pillow draws the numbered discs into the image. They live with the key, where `ingest` reads them.

`originalImage()` is **deleted**: a blind `.replace(/\.png$/, "-original.png")` is meaningless for a text question and is exactly the guessable-URL leak fixed in §4.4.

### 4.3 Answer keys — `web/lib/answer-key.ts` (new, server-only)

```ts
import "server-only";
import answersData from "@/data/answers.json";

export type BlankAnswerKey = {

  id: string; type: "mcq";

  rationale: string;                                   // shown after submit
  distractorNotes?: Partial<Record<OptionKey, string>>;

  confusables?: string[];  // near-miss phrasings that must NOT count

  rubric: RubricPoint[];

export type AnswerKey = BlankAnswerKey | McqAnswerKey | ShortAnswerKey;
export function getAnswerKey(id: string): AnswerKey | undefined { /* ... */ }
```

`RubricPoint` is deliberately the same idea one level up from `BlankKey`: `keywords` are the synonyms, `confusables` are the confusables, and §4.5's matcher is the same ladder.

**Alt-text trap:** alt text is public. An alt string reading "…showing the frontal, parietal, occipital and temporal lobes" hands the answer to every screen reader and every view-source. One line in the prompt (§3.5), one assertion in the data test (§8).

### 4.4 Keeping the key server-side

Four mechanisms, strongest first:

1. **`import "server-only"` at the top of `answer-key.ts`.** Highest value per line in this whole section: it converts "a Client Component imported the answers" from a silent leak that ships in the JS bundle into a build failure.
2. **Separate module, separate file.** Only `answer-key.ts` imports `answers.json`, and only the Server Action imports `answer-key.ts`.
3. **The Server Action returns results, never keys.** `GradeState` carries only what a student may see *after* submitting.
4. **A data test that fails the build** if the generator regresses — walk `questions.json` recursively, assert no object anywhere carries `answer`, `correct`, `rubric`, `modelAnswer`, `synonyms`, `confusables`, or `box`.

**The leak that exists today.** `web/public/questions/slide-01-diagram-1-original.png` is publicly fetchable at a name derived from the blanked file — anyone reads the key without submitting. Fix: reveals move to `web/data/reveals/` (outside `public/`), and the Server Action returns the reveal **as a base64 data URL inside the grade result**.

> Chosen over a signed-token route handler because it is five lines instead of forty and needs no secret, no expiry and no path sanitising; the cost is ~33% inflation on one PNG, bounded by capping the reveal render at 1200 px wide.

Neither approach stops a student submitting blank to reveal — nothing can without accounts — but both close the one-URL cheat, which is the difference between a demo that survives a question and one that doesn't.

### 4.5 Grading per type

**`web/lib/grading.ts` is not modified at all.** `normalize`, `editDistance`, `similarity`, `FUZZY_THRESHOLD`, `BlankKey`, `MatchKind`, `BlankResult`, `gradeBlank`, `gradeDiagram` are reused exactly as written, and the 13 existing Vitest cases are untouched and still pass.

| Type | Graded by |
|---|---|
| `diagram_blank` | `gradeDiagram(responses, key.blanks)` — **unchanged** |
| `table_blank` | `gradeDiagram` too: a table cell and a diagram label are the same `BlankKey` |
| `mcq` (with or without image) | `gradeMcq` — option-key match |
| `short_answer` | `gradeShortAnswer` — offline rubric coverage |

**MCQ — key by letter, never by text.**

```ts
// web/lib/grading-mcq.ts
export type McqResult = {
  chosen: OptionKey | null; correctKey: OptionKey; correct: boolean;
  rationale: string; note?: string;
  rejectedAs?: "empty" | "invalid";
};
export function gradeMcq(response: string, q: McqQuestion, key: McqAnswerKey): McqResult;
```

The wire value is a radio's option key, so there is nothing to normalise and no fuzzy matching: a value not in `q.options[].key` is `invalid`, an absent one is `empty`. **Do not grade by comparing option text** — that re-imports the confusable problem into a type that does not need it and breaks the moment options are reordered. **Option order is fixed at generation time.** If the UI shuffles per render the server can no longer map the posted letter back; shuffle once in the generator, store it, leave it.

**Short answer — rubric coverage, offline, no API call.**

```ts
// web/lib/grading-short-answer.ts
import { normalize, similarity, FUZZY_THRESHOLD } from "@/lib/grading";

export type PointResult = {
  id: string; text: string; weight: number; hit: boolean;
  matched: "exact" | "synonym" | "fuzzy" | null;
  rejectedAs?: "confusable" | "negated";
};
export type ShortAnswerResult = {
  points: PointResult[]; marks: number; total: number;
  modelAnswer: string; gradedBy: "rubric";
  rejectedAs?: "empty" | "too-long";
};
```

Same ladder as `gradeBlank`, over sliding windows instead of a single string:

1. `normalize()` the response once, split into tokens.
2. For each *n*-word keyword, scan every *n*-word window (plus *n*±1, to absorb an inserted article).
3. A window is rejected first if it equals one of the point's `confusables`; otherwise hits on equality, else on `similarity(window, keyword) >= FUZZY_THRESHOLD`.
4. **Negation guard:** a hit preceded within three tokens by `not`, `never`, `no`, `doesn't`, `isn't`, `cannot` is discarded as `negated`.

Marks are the summed weights of hit points. Cost is O(words × keywords) — instant and free, like the diagram path.

**Resolution of a real contradiction in CLAUDE.md:** its question-type table says `short_answer` is *"Claude-graded against rubric"*, its grading rule says *"never call the API during grading"*. For this prototype the rule wins outright, and not only on principle — **the deployed container holds no API key at all** (§6), so model grading is not merely disabled, it is impossible there. The rubric, keywords and confusables are produced once, at generation time, as extra fields in the same call that writes the question. Model-assisted marking is week 8 work, behind auth.

**State the limitation plainly in the report:** keyword coverage rewards name-dropping and cannot judge whether the reasoning is right. The negation guard catches the crudest false positive, not a confidently wrong relationship between two correct terms. The UI must therefore label the output "points covered", show the model answer beside it, and report `gradedBy: "rubric"`. The honest claim is automatic coverage checking to support self-assessment — not marking.

**The Server Action** (`web/app/questions/[id]/actions.ts`, rewritten) dispatches on `question.type` and returns a discriminated union:

```ts
export type GradeState =
  | ({ kind: "diagram_blank" | "table_blank"; results: BlankResult[];
       score: number; total: number; revealDataUrl: string | null })
  | ({ kind: "mcq" } & McqResult)
  | ({ kind: "short_answer" } & ShortAnswerResult)
  | null;
```

### 4.6 Changes to existing code

**`ingest/app/detect.py` — replace the placeholder title lookup with geometry.** `detect.py:279-281` is the failure; its three consequences are a null title in the UI, a null `title_box` that drops `Diagram.crop(..., keep_clear=…)`'s guard so crops slice through the heading, and the title surviving as a *label candidate* (the false-positive source). The rule that fits all four slides — verified: slide 1's title at y=187.2 (0.347 of height), slides 2–4 at y=36.0 (0.067), topmost text box in every case:

```python
def _find_title(slide, bounds: Box, max_words: int = 10) -> tuple[str | None, Box | None]:
    """Real decks use a plain text box, not a title placeholder — shapes.title is None."""
    best: tuple[float, str, Box] | None = None
    for shape in slide.shapes:              # top level only; titles are never grouped
        if not shape.has_text_frame:
            continue
        text = shape.text_frame.text.strip()
        box = _shape_box(shape, Transform())
        if not text or box is None or len(text.split()) > max_words:
            continue
        if box.y0 > bounds.height * 0.4:
            continue
        if best is None or box.y0 < best[0]:
            best = (box.y0, text, box)
    return (best[1], best[2]) if best else (None, None)
```

Then pass that box into `_walk` / `_is_label` so the title is excluded from label candidates — that is the part that fixes the false positive, not the display string. Tune the two thresholds with `python -m app.cli inspect`, which exists for exactly this.

**`ingest/app/cli.py` — two changes.**
- New `extract` command emitting `extract.json` (per slide: index, title, text objects, table rows, picture boxes) plus `page-NN.png` renders at zoom 2.0. This is the `assets` table in file form, and the input `web` generates from.
- `blank` gains `--plan blanks.json`: it reads the label indices and boxes Claude chose and draws those, instead of `cli.py:137-141`'s "first few in reading order". That is CLAUDE.md's `web → ingest` blank step done as a file handoff rather than a queue — same contract, no infrastructure. It writes blanked PNGs to `--images-out` and un-blanked copies to `--reveals-out`.

**Service boundary:** `ingest` gains no Anthropic dependency. Generation lives in `web/scripts/generate.ts`. Flow: `ingest extract` → `web generate` → `ingest blank --plan` → human review → commit.

**New and changed files:**

| File | Status |

### 5.2 The mixed quiz

One question per screen. On a 375 px phone a diagram plus its inputs already fills the viewport.

```
┌─────────────────────────────┐
│ ▓▓▓▓▓▓▓░░░░░░░░  3 of 7     │  ProgressBar
│ Diagram                     │  type badge
│                             │
│ Label the lobes of the      │  prompt, text-lg
│ brain.                      │
│ Brain_Anatomy_Sample.pptx   │  SourceRef (always visible)

│                             │
│ [   blanked slide image   ] │  QuestionImage
│                             │
│ ① [ your answer          ]  │  DiagramBlanks
│ ② [ your answer          ]  │
├─────────────────────────────┤
│ Skip            [  Check  ] │  sticky action bar
└─────────────────────────────┘
```

- **Order:** deck order (slide 2 → 3 → 4), types interleaved as generated. Do not group by type — a quiz that reads as one pass through the lecture is the point.
- **Flow:** `Check` grades → feedback renders in place → button becomes `Next` → last becomes `Finish` → `?q=done`.
- **Locking:** once checked, the answer is read-only; `Back` revisits it with feedback intact. No changing an answer after seeing the mark.
- **Skip:** tertiary text button, records an empty answer — `grading.ts` already returns `rejectedAs: "empty"`, no new path.
- **Sticky action bar:** fixed bottom on phones, inline from `sm:` up, `pb-[env(safe-area-inset-bottom)]` (needs `viewportFit: "cover"` in the layout's `viewport` export). Scroll region gets `pb-28` so the bar never covers the last input.
- **Results screen:** `5 / 7`, then one row per question — index, type badge, correct/partial/incorrect chip, one-line prompt, source ref. Tapping expands full feedback. Bottom: "Retry the ones I missed" and "Back to deck".

### 5.3 Per type

**Multiple choice** — radio group, whole row is the `<label>`. Rows `min-h-12`, selected row gets a 2 px ink border, not just a tint. After checking: correct option green left border + ✓, a wrong chosen one red + ✗, others dimmed, one-sentence rationale in an inset panel. An image MCQ is the same component with `QuestionImage` above it.

**Short answer** — `<textarea rows={5}>` at 16 px, word counter that only turns amber over the limit. After checking: a coverage banner, `3 / 4 points`, the per-point list, then a collapsed "Model answer" disclosure. Grading is local, so there is no pending state and no failure mode to design around.

**Diagram / table blanks** — numbered inputs matching the discs `blank.py` draws. Inputs need `autoCapitalize="off" autoCorrect="off" spellCheck={false} autoComplete="off"`: iOS silently rewriting `nucleas` → `nucleus` would erase the exact typo-tolerance behaviour the grader exists to demonstrate. After checking, the image swaps to `revealDataUrl`.

`question-form.tsx` currently prints only `correct` or the expected string, discarding `matched` and `rejectedAs`, which `grading.ts` already computes. Surface them — it costs nothing and is the clearest evidence the grading rules work:

| Result | Row text |
|---|---|
| `matched: "exact" \| "synonym"` | ✓ Correct |
| `matched: "fuzzy"` | ✓ Correct — spelling: **Occipital lobe** |
| `rejectedAs: "confusable"` | ✗ Close, but that's a different structure — **Occipital lobe** |
| `rejectedAs: "other-blank"` | ✗ That's the answer to blank 2 — **Occipital lobe** |
| `rejectedAs: "empty"` | — No answer — **Occipital lobe** |
| `matched: null` | ✗ **Occipital lobe** |

Never colour alone: every state carries an icon and words (WCAG 1.4.1).

### 5.4 Source reference (trust feature)

Rendered as a native `<details>` — no JS, works anywhere.

- **One rule:** for `diagram_blank` and image MCQs the expandable slide image is disabled until graded — opening the original mid-question hands over the answer. The reference text still shows.

### 5.5 Visual style

`web/app/globals.css` currently carries a `prefers-color-scheme: dark` block that flips the app dark on most students' phones — **delete it**, and set `color-scheme: light` on `<html>`. It also sets `body { font-family: Arial, Helvetica, sans-serif }`, which overrides the Geist font `layout.tsx` loads — drop that rule.

Tailwind v4 is CSS-first; tokens in `@theme`, no `tailwind.config.js`:

## 6. Wiring to the Cloudflare deployment

Commands run from the repo root; the lab VM had its own checkout.

### 6.1 Where `ANTHROPIC_API_KEY` lives

| Place | Value | Why |
|---|---|---|
| Mac, `web/.env.local` | the real key, `chmod 600` | The only machine that runs generation |
| Mac, `web/.env.example` | `ANTHROPIC_API_KEY=` (empty) | Committed, documents the name |
| Lab VM | **nowhere** | The VM never calls the Claude API |
| `compose.yaml` | **no change** | Neither service needs the key |
| Browser | never | No `NEXT_PUBLIC_` prefix; the generator is not part of the Next build |

The key is read by a Node script, not by Next.js, so `.env.local` is **not** auto-loaded (only `next dev` / `next build` do that). Load it explicitly:

```jsonc
// web/package.json
"generate": "node --env-file=.env.local scripts/generate.ts",
"test": "vitest run"
```

Node 26.7 on the Mac strips TypeScript types natively, so no loader is needed; `tsx` is the fallback. `--env-file` does not override an already-exported variable. (`web/Dockerfile` runs `node:22-slim` — irrelevant here, since the container never runs this script.)

Four independent barriers, three already in the repo:

1. **Git** — `.gitignore:2-4` is `.env`, `.env.*`, `!.env.example`; `git check-ignore` confirms `web/.env.local` is matched.
2. **Docker build context** — `web/.dockerignore` lists `.env*`, so no env file can enter an image layer.
3. **The browser** — Next inlines only `NEXT_PUBLIC_*`; the key is never read during `npm run build` at all.
4. **The VM** — has a read-only deploy key and never needs a credential that spends money.

If a later milestone makes the running app call Claude, the key goes to `/srv/ai-study-platform/.env` (root-owned, `chmod 600`) and reaches the container as a **runtime** variable — `env_file:` plus `environment: [ANTHROPIC_API_KEY]`. **Never `build.args`**: build args bake into image layers and are readable via `docker history`.

### 6.2 Why generation is offline, not in the app

- **There is no auth.** An in-app "Generate" button is an unauthenticated money-spending endpoint on a public URL. SESSION.md records scanners finding the earlier tunnel within minutes (cPanel, `php-cgi.exe`, `/actuator/env` probes). No rate limit fixes that.
- **It keeps the key off a shared school lab VM** with an instructor-controlled idle agent.
- **The deck cannot reach the VM anyway** — `.gitignore:31` (`*.pptx`) keeps lecture material local by design.
- **Generation is slow and bursty** (LibreOffice plus vision calls) and there is no queue, job table or progress UI.
- **Committed questions are reviewable.** The answer key lands in a diff a human checks before students see it, and re-serving costs nothing. This is the cheapest possible guardrail against a bad box or a wrong confusable, and it disappears the moment generation moves in-app.

**The tradeoff, stated honestly:** visitors to the public URL cannot upload their own deck. The demo serves a fixed, curated set. That is the correct week-7 trade — upload → queue → worker is W8–9 — and this wiring is forward-compatible because the artifact shape already matches the `questions` table.

Per deck:

```bash
  -v "$PWD:/repo" ingest:dev \

    --images-out /repo/web/public/questions \

git add web/data/questions.json web/data/answers.json web/data/reveals web/public/questions

# 5. Redeploy. launch.py pulls, rebuilds, health-waits, prints URL + QR.
ssh labvm "wsl -d Ubuntu-24.04 -u root python3 /srv/ai-study-platform/scripts/launch.py"
```

### 6.4 Rebuild, not restart

`web/lib/questions.ts` does a **static import** of `@/data/questions.json`, so the question set is compiled into the standalone server bundle by `npm run build`; `web/Dockerfile` does `COPY . .` before the build and the runtime stage copies `/app/public`.

| Command | Picks up new questions? |
|---|---|
| `docker compose restart web` | **No** — same image |
| `docker compose up -d` (no `--build`) | **No** |
| `docker compose up -d --build` | **Yes** |
| `scripts/launch.py` (default) | **Yes** — its up path is `up -d --build` |
| `scripts/launch.py --no-build` | **No** — never use it after regenerating |

A bind-mounted volume for `public/` was rejected: it would let served state drift from git-tracked state, and WSL path mounts add a failure mode for no benefit.

The public hostname normally survives a questions-only redeploy — only the `web` image changes, so the `tunnel` container is not recreated. Don't rely on it: `launch.py` prints the live URL at the end of every run, and `shutdown.py` (a `compose down`) always yields a new one.

## 9. What a human must do

None of this is automatable.

1. **Create an Anthropic API key in a dedicated workspace.** Console → Settings → Workspaces → Create workspace, then create the key scoped to it. Spend limits **cannot be set on the Default Workspace**, so a key created there has no cap at all.
2. **Set the spend limit before the first run, not after.** Recommended: $20/month with an alert at 50%. Also set the workspace's output-tokens-per-minute rate limit — the one backstop a bug in the generator cannot defeat.
3. **Paste the key into `web/.env.local` by hand** and `chmod 600` it. It goes nowhere else, ever.
4. **Review the generated answer key and every blanked image before committing.** Claude picks the blanks, synonyms and confusables. A wrong answer key is worse than no question, and this review is the only guardrail in the system.
5. **Power on the lab VM.** Azure Lab Services' idle agent shuts it down; `restart: unless-stopped` brings the stack back, but nothing powers the machine on remotely.
